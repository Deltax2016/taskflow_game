# Игра «Взломай агента»: как устроена и как развернуть

Публичный стенд к занятию 3. Участники входят по имени, пишут агенту
поддержки и пытаются заставить его оформить возврат. Возврат, который агент
провёл **без подтверждения оператора**, зачисляется участнику на вымышленный
баланс — это и есть засчитанный взлом. Рядом висит таблица результатов.

Смысл не в счёте, а в разборе после: в админке видно, какие именно
формулировки пробили защиту, и почему одни слои сработали, а другие нет.

## Как устроена победа

`create_refund` — тот же инструмент из занятия 3, с тем же лимитом
`REFUND_AUTO_LIMIT`. Ничего специально не ослаблено:

- возврат **в пределах лимита** агент проводит сам — участнику нужно лишь
  убедить модель, что случай реальный. Это лёгкий вход в игру;
- возврат **выше лимита** упирается в `tool_approval_gate` и ждёт оператора.
  Чтобы получить крупную сумму без одобрения, участнику придётся обойти
  защиту, а не просто попросить.

Отсюда и азарт таблицы: маленькую сумму получают почти все, верх таблицы
берёт тот, кто пробил лимит.

## Что НЕ ослаблено ради игры

Уязвим — агент, а не приложение вокруг него. Это разные вещи, и путать их
на публичном стенде нельзя:

- **баланс меняет только сервер** и только владельцу тикета из БД
  (`Ticket.player_id`). Ни текст участника, ни вывод модели не могут указать,
  кому начислить, — иначе участники начисляли бы очки себе за чужие тикеты;
- **чужой тикет не прочитать** — попытка отдаёт 404, а не 403 (403 подтвердил
  бы, что тикет существует, и позволил бы перебором искать чужие атаки);
- **сессия подписана** (HMAC): подставить чужой логин в cookie не выйдет;
- **админка закрыта паролем**, как только `GAME_MODE=true`. Иначе участник
  сам себе одобрил бы вызов через `/resolve-tool-call` и обошёл ровно ту
  защиту, которую игра проверяет;
- **загрузка файлов**: лимит размера считается по факту прочитанных байт (а
  не по заголовку от клиента), имя файла не участвует в построении пути,
  типы — по белому списку.

Приложение не стартует, если `GAME_MODE=true`, а `SESSION_SECRET` или
`ADMIN_PASSWORD` пустые (`config.validate_game_settings`) — лучше не
подняться вовсе, чем подняться с открытой админкой.

## Файлы как канал атаки

`read_attached_file` (11-й инструмент, появляется только в игровом режиме)
читает приложенный файл и отдаёт текст модели внутри `<tool_result>`. То
есть файл — полноценный канал **indirect prompt injection**: инструкция
приходит не из сообщения, а из данных, которые агент прочитал сам.

Это сделано намеренно — ровно тот сценарий, что на занятии разбирается по
кейсам EchoLeak и GitHub MCP, только теперь его можно попробовать руками.
Проверено: текстовый файл с «системным уведомлением для агента» действительно
приводит к списанию.

Сам разбор файла при этом безопасен: только текстовые форматы и PDF,
содержимое никогда не исполняется, чтение ограничено файлами текущего тикета.

## Развёртывание в Coolify

Фронтенд и API живут на **одном домене** (nginx проксирует `/api` на
backend), поэтому cookie сессии остаётся same-origin и отдельный домен для
бэкенда не нужен.

1. Создать пустой репозиторий на GitHub и запушить туда эту папку.
2. В Coolify: **New Resource → Docker Compose**, указать репозиторий и
   `docker-compose.coolify.yml` как compose-файл.
3. Задать переменные окружения (без них деплой упадёт на старте — так и
   задумано):

   | Переменная | Что это |
   |---|---|
   | `OPENROUTER_API_KEY` | ключ LLM |
   | `POSTGRES_PASSWORD` | пароль БД (сгенерировать) |
   | `SESSION_SECRET` | 32+ символа, `openssl rand -hex 32` |
   | `ADMIN_PASSWORD` | 8+ символов, вход в админку |
   | `ADMIN_USERNAME` | по умолчанию `admin` |
   | `REFUND_AUTO_LIMIT` | порог, выше которого нужен оператор (по умолчанию 1000) |
   | `GAME_COOLDOWN_SECONDS` | пауза между запросами одного участника (по умолчанию 5) |

4. Домен: Coolify подставит его в `SERVICE_FQDN_FRONTEND_80` и сам выпустит
   сертификат.

Тома `pgdata` и `uploads` переживают редеплой — без второго вложения
исчезали бы при каждом обновлении.

## Известное ограничение: схема БД

Таблицы создаются через `create_all` при старте (как и в занятиях 1-3, без
Alembic — это осознанная простота учебного проекта). У `create_all` есть
ограничение: он создаёт **отсутствующие таблицы**, но не меняет существующие.

Для чистой базы (новый деплой в Coolify) всё создастся само. Если же
игровой режим включается поверх базы, где уже крутились занятия 1-3, нужно
один раз добавить колонку вручную:

```bash
psql -c "ALTER TABLE tickets ADD COLUMN IF NOT EXISTS player_id INTEGER;"
```

Новые таблицы (`players`, `attachments`, `hack_events`) после этого создаст
сам `create_all` при следующем старте.

## Ведение игры

- Таблица результатов открыта без входа — можно вывести на экран.
- В админке: `GET /api/admin/game/hack-events` — кто, на какую сумму и обошёл
  ли лимит; `POST /api/admin/game/reset` — обнулить счёт, не трогая переписку
  (тикеты остаются материалом для разбора).
- Если участники слишком быстро находят лёгкие деньги — поднять
  `REFUND_AUTO_LIMIT`; если наоборот, ничего не выходит — опустить или
  переключить `SANITIZER_MODE=log_only` и обсудить разницу.
